# 折りたたみ時の最低高を使った試作

この試作の採用は見送る。
通常の開閉では余白を減らせたが、画面より上にある長い行が折り返し直されると、必要なスクロール範囲が足りなくなった。
最低高方式全般が不可能という結論ではなく、今回の「折りたたみ時のscrollTopを一つ保持する」実装では不足するという結果である。

## 試した構成

製品の`src`は変更せず、vault外にコピーしたソースを試作用にビルドした。
既存の`.cm-sizer`はタイトル・Properties・本文を含み、スクロール領域の直下にある。
この要素へ`min-height: calc(100% + <折りたたみ前のscrollTop>px)`を適用した。
Obsidianの通常の下端paddingは維持し、本文が増えれば最低高による空白を自然に埋める。
上へスクロールした場合は保持値を下げ、通常の下スクロールでは増やさない。

ズームでは既存のscroll targetを使って必要な高さを計算した。
階層ごとの高さの履歴、独自overlay、折りたたみ後の手動scrollTop補正は追加していない。
最初の試作では短い項目のズーム位置が3px下へずれたが、行の外枠ではなくカーソルの描画位置から必要量を求めることで解消した。

## 通常の操作では改善した

Obsidian 1.14.0のdesktop Live Preview、DPR 2、900×700pxのウィンドウで比較した。
対象項目をスクロール領域上端から約160pxへ置いた場合の結果は次のとおり。

| 測定対象                                       |  現行版 |  試作版 |
| ---------------------------------------------- | ------: | ------: |
| 閉じた状態の本文領域内の下端空白               | 597.5px | 192.9px |
| 開いた状態の本文領域内の下端空白               | 597.5px |   100px |
| 閉じた状態の文末からスクロール可能領域末尾まで | 840.7px | 435.7px |
| 開いた状態の文末からスクロール可能領域末尾まで | 840.7px | 342.7px |
| 開閉時の操作行の位置ずれ                       |     0px |     0px |

本文領域の外にもObsidian既存の余白があるため、100pxを「全体の空白」とは扱わない。

基本18チェックが成功した。
対象行を100・160・400pxへ置いた開閉、短い子から親へのズームアウト、全体表示への復帰、幅と高さの変更を含む。
既存のリサイズ検証スクリプトもPropertiesの有無それぞれで実行した。
試作版用のコピーでは、paddingを増やすこと自体の期待値を通常paddingの維持へ変更し、表示行とその画面位置の検証は残した。

追加で、ガイドによる6枝の一括開閉、native controlでの10往復、ガイド操作無効時のnative開閉、下スクロールで余白が増殖しないことを確認した。
外部編集によるズーム解除、同じペインでのファイル変更、ズーム中のplugin再読込でも保持値が解除された。

## 採用を止めたケース

短いファイル名、Propertiesなしのノートで、長いリスト行65個、短いanchor行12個、末尾の親子リストを用意した。
長い行には`Text above the viewport must reflow when the pane becomes narrow. `を6回繰り返した。
末尾の親を画面上端から159.5pxに置いて閉じ、ウィンドウ幅を900pxから500pxへ縮めた。
高さは700pxで固定した。

| 測定対象              |  現行版 |     試作版 |
| --------------------- | ------: | ---------: |
| 縮小前の親のY座標     | 159.5px |    159.5px |
| 縮小後の親のY座標     | 159.5px |    252.5px |
| 位置ずれ              |     0px |   **93px** |
| 縮小後のscrollTop     |  8268px |     8175px |
| 縮小後の最大scrollTop |  8672px | **8175px** |

試作版のscrollHeightは8797px、viewportは622pxだった。
その差8175pxが実際のscrollTopと一致し、スクロールが上限へ制限されたことを確認できる。
本来必要な8268pxとの差93pxが、そのまま親項目の位置ずれになっている。

保持した7692pxという値だけでは、折り返し後に増えた必要量を表現できない。
表示行を基準に再計算するなど、レイアウト変更へ対応する追加の仕組みを検討する必要がある。
今回の小さな置き換えとしては採用せず、製品実装を維持する。

## 検証の範囲と記録

操作はリポジトリのテストvaultに限定したObsidian CLI/CDPで実行した。
native handlerへpointer sequenceを渡し、ズームには実際のObsidian commandを使った。
Macがロック中のため、Computer Useによる実クリックは行っていない。
通常開閉は16ms間隔と同期時点で計測したが、すべての描画フレームを録画したものではない。
上記の切り分けた幅縮小は変更後の安定した値の比較であり、途中の全フレームは未確認。
mobile、見出し、空白部分への文字入力も未確認。

別の幅変更往復では現行版にも位置ずれがあったため、「現行版はリサイズ全般で問題ない」とは結論しない。
また、Obsidian CLIの応答待ちで停止した試行は成功件数から除き、単独の縮小操作で比較を取り直した。

集約した測定値は[results.json](results.json)に保存した。
使い捨てのソース、差分、実行スクリプト、元の測定ログは`/tmp/obsidian-bullet-fold-floor-aw62l_fr/`に残してある。
製品化前には、内部scroll targetの型への依存、非同期計測までの編集による位置の変化、DOM classを使ったズーム検出も見直す必要がある。

終了時にはテスト用Obsidianのプロセス終了を確認し、ノート・設定・pluginの八ファイルを元へ戻した。
復元直後と2秒後の両方で、バックアップとのハッシュ一致を確認した。
